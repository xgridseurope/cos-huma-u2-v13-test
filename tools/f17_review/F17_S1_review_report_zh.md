## 1. Codex 的根因和解决办法对不对

**根因：正确。** 我独立复现了 Codex 的 S1 路径（l02 g1-troba → g1-maxil，点模型和离开在同一个 JavaScript 任务里），连续 3 次都失败。g1-maxil 原本禁用的「Continua」在离开后约 0.9–1.7 s 被旧流程点亮，和 Codex 观察到的约 1.2 s 一致。

在 Codex 的基础上补充两点更精确的源码证据（`curs/player.js`）：

- 第 250 行 `await wait(700)` 之所以拿到新的生命周期编号，是因为它**创建得太晚**。我记录了「离开」和「创建 700 ms 等待」的先后：
  - 同一任务：离开约 48 ms，创建等待约 49 ms（等待在离开之后创建）。
  - 原生边界 / 真实触屏：创建等待 55 ms / 1729 ms，离开 468 ms / 2738 ms（等待在离开之前创建）。

  原因：答对时 `tapTask` 同步触发 `done` 事件，但 `sequence` 里 `await new Promise(done)` 之后的代码要等当前整段脚本跑完才执行。同一任务里，这段脚本已经点了「离开」、调用了 `render()`，生命周期编号已经换成新的了。
- 第 247 行循环开头的 `if (!ok()) return` 也有问题：发现自己过期后，`sequence` 正常返回，等于告诉调用方「已完成」。g1-troba（第 282 行）于是执行 `feedback()` 和 `setNext(true)`，解锁了新步骤。

**解决办法：方向正确，但覆盖不全。** Codex 建议「在每个 `await sequence()` 返回后核对编号」。我把它做成原型 P2，在 `player.js` 的 6 个调用点各加一次检查，结果：

- `player.js` 里的路径（T1 ×3、T1b、T1c）全部修好；
- **l07.js:77 里课程自己调用的 `c.sequence` 仍然失败**（T5：gA-explica 的「Continua」被解锁）。

要彻底修好，必须逐个修改课程文件里的调用点，其中包括已经冻结的 `l10.js:118`。所以我建议复用 Codex 的「生命周期编号」思路，但把检查放进 `sequence()` 内部，一处修复就覆盖全部 8 个调用点，不用改 l10。

## 2. 我的独立判断和证据

**结论：测试构造超出了正常事件边界，同时生产代码存在潜在缺陷，两者都有。**

- 浏览器把每次触屏或点击作为独立任务分发，每个事件处理完之后，会先把排队中的后续步骤（`await` 之后的代码）跑完，再处理下一个事件。「点模型」和「点离开」不可能落在同一个任务里。
  - 原生边界（独立任务、间隔 0 ms）：3/3 通过。
  - 真实触屏：通过。
  - Codex 的原生触屏对照：同样通过。
- 现有代码里只有 `tapTask`、`ladderChoice` 和自评按钮会触发 `done`，它们都不会在同一个任务里切换步骤。所以以现在的代码，真实儿童操作触发不了 S1。
- 但 `sequence()` 能否拦住过期流程，依赖事件的执行顺序，自己不做检查，而且发现过期时会报告「已完成」。以后只要加一条同一任务里先触发 `done` 再切换步骤的路径（比如「自动下一步」），就会变成真实缺陷。应当修复。

**我之前 S1 测试误报 PASS 的原因（测试缺陷）**
- `tools/f17_race.py` 的 S1 在离开之后，要经过好几次浏览器往返才读到「新步骤的初始状态」。这时旧流程（0.9–1.7 s）可能已经把按钮点亮了，前后两次读到的都是「已点亮」，比较结果是「没变化」，于是 PASS。
- 修正：离开的同一时刻，在页面内记录新步骤的初始状态（`window.__init_can`），以它作为比较基准。
- 修正后的 S1 在基线 `b75f88a` 上失败（`False → True`），在 P1 上通过。

## 5. 其他缺陷：已证实和潜在风险

**已证实**
- **l11 弯手臂按钮（`relacio.js` 的 `bend()`）**：离开后旧动画继续修改新步骤的手臂姿势，真实触屏可触发。基线上 T6 失败，P1 上通过。影响只在模型姿势，持续约 0.5–1.4 s；不涉及按钮、评分和学习记录。

**已排查，结论为安全**
- l12「v-ordre / r-ordre」信号演示途中离开：下一步 `recall()` 自己会调用 `hidden()`，从而执行 `sig.clear()`，旧信号被清除（T7 在基线上也通过）。我起初的静态判断是有风险，被测试推翻。
- `ladderChoice`、`tapTask` 演示之后的代码：调用演示前已经同步记下编号，演示之后会检查。
- 2.2 s 和 2.5 s 的等待，以及 l05、l06、l07 演示里的等待：都在用户事件处理中同步创建，编号正确。
- `choiceSeries`：已有检查，和 P1 不冲突。

**潜在风险（未证实，不建议本轮修改）**
- `relacio.js` 的 `leg()` 信号动画只靠新步骤调用 `hidden()` 来清除。目前所有演示之后的步骤都会调用，但以后新增一个不调用 `hidden()` 的步骤，就会出现残留。可选的加固改动保存在 `diffs/P1_full.diff`（`leg` 部分），没有放进最小修复。
- 生命周期编号在 `wait()` 被调用时才确定（不是在流程开始时确定）。以后凡是「`await` 一个外部 Promise，然后再 `wait()`」的新代码，都要先核对编号。建议写进 HANDOFF 的开发规则。
